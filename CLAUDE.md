# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Platform Reality

EasyHDR is a Windows-only Rust desktop app (edition 2024, `rust-version = 1.93`). Every real
capability — HDR toggling, process enumeration, UWP packages, tray icon, registry autostart — sits
behind `#[cfg(windows)]`. The crate still *compiles* elsewhere because each Windows path has a
`#[cfg(not(windows))]` stub or mock sibling, so a green `cargo check` on macOS/Linux proves nothing
about Windows behaviour. `.github/workflows/ci.yml` (`windows-latest`) is the authority.

On a non-Windows host, cross-check against the MSVC target as `prek.toml` does:

```bash
cargo xwin clippy --target x86_64-pc-windows-msvc --all-targets --all-features -- -D warnings
cargo xwin check --lib --target x86_64-pc-windows-msvc
```

## Essential Commands

```bash
cargo fmt --all -- --check                                # CI gate 1
cargo clippy --all-targets --all-features -- -D warnings  # CI gate 2 — clippy::pedantic, warnings are errors
cargo build --release
cargo test --lib --release                                # unit tests; safe in parallel
```

Integration tests in `tests/` touch Windows API global state and **must** be serialized, one target
at a time:

```bash
cargo test --test integration_tests --release -- --test-threads=1
```

CI runs exactly these five targets sequentially: `integration_tests`, `version_detection_tests`,
`memory_usage_test`, `startup_time_test`, `cpu_usage_test`. `icon_cache_tests` and
`uwp_process_detection_tests` are **not** in CI — run them locally when touching those subsystems.

```bash
cargo test --lib test_config_path                                   # single unit test by name filter
cargo test --test integration_tests --release -- --test-threads=1 \
  --exact test_config_persistence_integration                       # single integration test
cargo bench                                                         # Criterion, 5 targets in benches/
cargo bench -- --save-baseline ci-baseline                          # harness=false enables Criterion args
cargo deny check                                                    # licenses + advisories (deny.toml)
cargo +nightly fuzz run fuzz_config_json -- -max_total_time=60      # 3 targets under fuzz/
MIRIFLAGS="-Zmiri-disable-isolation -Zmiri-symbolic-alignment-check" \
  cargo miri test --lib error -- --test-threads=1                   # only `error` is a required Miri gate
prek run --all-files                                                # all git hooks (prek, not pre-commit)
```

Miri is only *required* to pass on the `error` module. The full-coverage Miri job is
`continue-on-error` because Windows FFI cannot run under Linux Miri and rayon (pulled in via
slint → image) trips Stacked Borrows.

## Architecture Overview

`src/lib.rs` exports `config`, `controller`, `error`, `hdr`, `monitor`, `utils`, and `uwp`
(Windows-only). **`src/gui/` is declared only in `src/main.rs`, not in the library** — Slint code is
generated by `build.rs` and pulled in via `slint::include_modules!()` in the binary. Integration
tests under `tests/` therefore cannot reach GUI code; anything that needs test coverage must live in
the library.

Startup wiring happens in `initialize_components` (`src/main.rs`). Three bounded
`mpsc::sync_channel(32)` links connect four threads:

```text
ProcessMonitor  --ProcessEvent-->  AppController  --AppState-->  GuiController (main thread)
HdrStateMonitor --HdrStateEvent->  AppController
```

- `AppController` runs on its own thread (`AppController::spawn_event_loop`) and owns all HDR
  decisions, including the 500 ms debounce that suppresses disable-on-restart churn.
- `Arc<RwLock<WatchState>>` is shared between `AppController` and `ProcessMonitor`; the controller
  writes the enabled-app watch list, the monitor reads it each poll cycle.
- The GUI holds `Arc<Mutex<AppController>>` (parking_lot) and owns the main thread via
  `gui_controller.run()`.

`HdrController` (`src/hdr/controller.rs`) branches on `WindowsVersion`
(`Windows10 | Windows11 | Windows11_24H2`) for every display operation, because 24H2 uses a
different Display Configuration API path. Add new HDR operations as the same three-way match, not as
a single call site.

State lives outside the repo: config at `%APPDATA%\EasyHDR\config.json`, icons at
`%APPDATA%\EasyHDR\icon_cache\{uuid}.png`.

## Project Boundaries

| Area | Rule |
| --- | --- |
| `ui/main.slint` | Sole UI source; `build.rs` regenerates bindings into `target/` on every build. Edit the `.slint` file, never the generated output. |
| `src/gui/` | Binary-only. Don't add `pub mod gui` to `src/lib.rs`; move logic that needs test coverage into a library module instead. |
| `src/hdr/windows_api.rs`, `src/uwp/` | Raw Win32 / WinRT FFI. `unsafe` is permitted across the crate but every site carries `#[expect(unsafe_code, reason = "...")]` naming the specific FFI purpose. |
| `Cargo.lock`, `.cargo/audit.toml`, `deny.toml` | Advisory ignores carry justification comments — extend, don't prune. |
| `proptest-regressions/` | Generated failure seeds; commit them, don't edit. |

## Common Change Workflows

### Adding a user preference

The settings path is wired by positional callback arity and breaks in five places at once:

1. Add the field to `UserPreferences` in `src/config/models.rs` with `#[serde(default)]` (old config
   files must still deserialize) and to its `Default` impl.
2. Add matching `in-out property` declarations to **both** `SettingsDialogContent` and `MainWindow`
   in `ui/main.slint`, and extend the `save-settings(...)` callback signature.
3. In `src/gui/gui_controller.rs`: seed the initial value with `main_window.set_settings_*`, widen
   the `on_save_settings` closure parameter list, and widen **both** `save_settings` functions — the
   `#[cfg(windows)]` implementation and the `#[cfg(not(windows))]` stub.
4. Persist through `AppController` so config save and GUI state update both fire.
5. Run `cargo clippy --all-targets --all-features -- -D warnings` — Slint's generated bindings surface
   arity mismatches as compile errors here first.

### Adding or changing a monitored-app kind

`MonitoredApp` is an enum (`Win32(Win32App) | Uwp(UwpApp)`) with **hand-written** `Serialize` /
`Deserialize` in `src/config/models.rs`. The deserializer is `#[serde(untagged)]` over a helper and
migrates the pre-enum flat JSON layout into `Win32App`. Adding a variant means updating that helper,
the `Display` impl, the `AppIdentifier` mapping in `ProcessMonitor::update_watch_list`, and the
matching arms in `AppController`. Keep `test_backward_compatible_deserialization` passing.

### Mutating the monitored-app list

`add_application`, `remove_application`, and `toggle_app_enabled` on `AppController` each perform the
same four steps: mutate `config`, `save_config_gracefully()`, `update_process_monitor_watch_list()`,
`send_state_update()`. Follow that order for any new mutation — skipping the watch-list refresh
leaves `ProcessMonitor` polling a stale set.

## Repository Conventions

- **Errors:** `thiserror` enums in `src/error.rs` (`EasyHdrError`, `IconCacheError`), both
  `#[non_exhaustive]`, with `#[source]` on every wrapped cause. Library code returns
  `easyhdr::Result<T>`; `src/main.rs` uses `anyhow` with `.context(...)`. Any user-visible error
  variant also needs an arm in `get_user_friendly_error` — that match is exhaustive.
- **Lints:** `unsafe_code` and `missing_docs` are `warn` at crate level, and clippy runs with
  `pedantic` plus `unwrap_used`. Suppress with `#[expect(..., reason = "...")]` and a real reason,
  matching existing sites; a bare `#[allow]` is not the house style.
- **Config writes:** go through `ConfigManager::save`, which writes to a temp file and renames.
  Do not `fs::write` the config path directly.
- **Icon caching:** use `IconCache::cache_icon_gracefully` / `IconCache::new(IconCache::default_cache_dir())`.
  Cache failures degrade gracefully and must never fail the calling operation.
- **Tests that touch `%APPDATA%`:** use `easyhdr::test_utils::AppdataGuard`, which holds a global
  mutex and restores the original value on drop. Setting the env var directly races other tests.
- **HDR-dependent tests:** construct via `HdrController::new_mock()` or
  `AppController::new_with_mock_hdr(...)` rather than real display enumeration.
- **Git hooks:** `prek.toml` (not `.pre-commit-config.yaml`) enforces fmt, clippy, gitleaks,
  conventional commit messages, and blocks direct commits to `main`/`master`; `cargo test --lib` runs
  at pre-push. Install with `prek install`.

## Critical Gotchas

- **Do not parallelize the integration tests.** Windows Display Configuration and Toolhelp32 APIs
  carry process-global state; `--test-threads=1` per target is required, and CI runs the targets one
  command at a time rather than as a single `cargo test` invocation.
- **`.github/workflows/profiling.yml` triggers on `src/monitor/**` and `src/controller/**`.** Changes
  there kick off flamegraph and DHAT jobs on `windows-latest`; keep `tests/cpu_profiling_test.rs` and
  `tests/dhat_profiling_test.rs` compiling and their profiled function names
  (`profile_process_monitoring_hot_paths`, `profile_production_allocation_patterns`) stable, since the
  workflow invokes them by `--exact` name.
- **`release` profile uses `panic = "abort"`.** Code that relies on unwinding across a thread boundary
  will terminate the process in release builds; propagate failures as `Result` instead.
- **Windows build gate:** `src/main.rs` refuses to start below build 19044 (`MIN_WINDOWS_BUILD`).
  New APIs must be available on Windows 10 21H2 or guarded by a `WindowsVersion` branch.
